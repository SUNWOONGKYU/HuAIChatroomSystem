## 왜 이렇게 갈라져 있나

**bot-service 는 텔레그램에서 직접 당겨온다(polling).** 웹훅은 공개 HTTPS 주소가 있어야
하는데, `cloudflared` 같은 무료 임시 터널은 계정 없이 5분이면 뚫리지만 URL이 재시작마다
바뀌고 아무 통보 없이 그냥 끊긴다(실측: 며칠간 끊긴 채 아무도 몰랐다). polling은 그 외부
의존이 아예 없다 — `BOT_SERVICE_RECEIVE_MODE=polling`이 기본값이고, 공개 주소를 열어야
하는 웹훅은 그게 꼭 필요한 배포(공인 도메인이 있고 안정적으로 열어둘 수 있는 경우)에서만 쓴다.

**웹 산출물은 완료 승인 전엔 프리뷰로만 공개된다.** 실행이 끝나자마자 프로덕션에 바로 올리면
방장이 협업 운영센터에서 승인 버튼을 누르기도 전에 결과물이 이미 공개 주소로 떠 있는 상태가 된다. 그래서 이제는
프리뷰만 먼저 올리고(방장이 눌러서 미리 볼 수 있다), 완료 승인이 실제로 기록된 뒤에만
local-gateway 의 폴러가 그 배포를 프로덕션으로 승격한다.

**bot-service 와 local-gateway 가 같은 PC 에 있다.** 그래서 bot-service 가 방 기억
(`sessions/rooms/…_위키.md`)을 디스크에서 바로 읽고, 문서 산출물도 그 자리에서 텔레그램에
올린다. 둘을 떼어놓으면 이 두 경로가 끊긴다.

**게이트웨이는 방마다 하나다.** 자기 `gateway_id` 로 온 일만 리스하고 자기 폴더 안에서만
실행한다. 개인회생 방의 실행이 회계 자료 폴더를 열 수 없고, 그 반대도 마찬가지다.

**`/healthz`와 `/readyz`는 다른 질문에 답한다.** bot-service(8787)·local-gateway(8797)
둘 다 두 엔드포인트를 함께 둔다. `/healthz`는 "프로세스가 살아있는가"만 보는 liveness라
Telegram 수신이 멎었거나 Supabase가 끊겨도 200을 낸다. `/readyz`는 실제로 의존성을
확인한다 — bot-service는 Supabase 왕복(가벼운 조회)과 수신 경로(polling 마지막 성공
시각 또는 webhook 등록 상태)가 둘 다 살아 있어야 200이고, local-gateway는 대기 작업을
리스 시도해 Supabase 도달성을 확인한다. `curl 200`만 보고 "동작한다"고 판단하면 안
된다는 이 저장소의 원칙을 엔드포인트 계약으로 옮긴 것이다.

**방은 6시간마다 통째로 백업된다.** bot-service가 상주 루프로 `status=active`인 방마다
13개 테이블(작업·이벤트·승인·산출물·멤버·역할·제안 등)을 모아 로컬 디스크
(`sessions/rooms/recovery/<방>/<시각>.json` + 체크섬 사이드카 `.sha256`)에 쓰고, 같은
스냅샷 사실을 Supabase `huai_recovery_snapshots` 장부에도 남긴다. 파일과 장부 모두
방당 최근 240개(6시간×4회×60일)만 남기고 오래된 것부터 자동 정리한다. 복구는
`scripts/restore-room-backup.mjs`로 하며 기본은 dry-run이다(`--apply`를 명시해야 실제로
Supabase에 쓴다). 체크섬을 파일 옆에 같이 두는 이유는, 복구가 실제로 필요한 상황(DB가
망가졌거나 접근이 안 되는 상황)에서 정작 DB에 있는 체크섬을 못 꺼내는 사태를 막기
위해서다.

**협업 운영센터와 산출물은 Vercel 에 있다.** 텔레그램의 예전 고정 협업 운영센터 메시지는 제거했고,
봇 메뉴 `/center`와 작업 메시지 링크가 현재 진입점이다. 포럼 주제에서 `/center`를 실행하면
roomId와 threadId를 함께 전달해 해당 주제의 작업만 연다.

역할은 LeaderBot(최근 대화 기반 계획·제안), ClaudeBot/CodexBot(파일 작업 실행), Gemini 웹(응답 전용 계획·검토), AuditBot(독립 검증)으로 분리한다. Telegram은 지시·접수·진행 알림만 보내고 승인·보완·취소는 협업 운영센터에서만 처리한다. 고위험 작업만 3문항 퀴즈를 거친다.

`*.supabase.co` 는 HTML 을 `text/plain` 으로 강제해서
올려도 소스만 보인다 — 게임을 올려도 실행되지 않는다.

**대화 원본은 Storage, 요약은 파일, 색인은 DB.** 원본은 무손실 사본이라 지우기 전 반드시
있어야 하고(텔레그램은 지난 대화를 돌려주지 않는다), 요약은 읽히기 위한 손실 압축이라 DB
용량을 쓰지 않는다.

## 데이터가 어디에 남나

| 무엇 | 어디 | 지우나 |
|---|---|---|
| 작업·승인·산출물 링크·보고 전문 | Supabase 표 | 안 지움 |
| 통신 기록(이벤트·아웃박스·수신 원본) | Supabase 표 | 60일 후, 보관 확인된 것만 |
| 대화 원본 jsonl | Supabase Storage + 로컬 | 안 지움 |
| 하루치 요약 위키 | 작업 PC `sessions/rooms/` | 안 지움 |
| 방 백업 스냅샷(13개 테이블, 6시간마다) | 작업 PC `sessions/rooms/recovery/` + Supabase `huai_recovery_snapshots` 장부 | 방당 최근 240개만, 넘으면 오래된 것부터 |
| 웹 산출물 | Vercel huai-artifacts | 안 지움 |

방별 최신 40턴과 최신 승인 이벤트는 나이와 무관하게 남긴다 — 리더가 읽는 창과 작업 재개
커서다. 조용한 방이 그걸 잃으면, 방장 눈에는 텔레그램에 대화가 그대로 보이는데 봇만 기억을
잃은 상태가 된다.
