# Telegram 전환 요구사항 — 휴먼-AI 협업 채팅룸 시스템

## 1. 변경 목적

현재 개발 중인 휴먼-AI 협업 채팅룸 시스템의 주 사용자 화면을 별도 웹/PWA에서 Telegram 프로젝트방으로 변경한다.

최종 구조는 사람 참여자와 역할별 AI 봇 여러 개를 하나의 Telegram 프로젝트방에 초대하고, 중앙 오케스트레이터가 각 봇의 발언, 작업 배정, 승인, 검증, 완료 흐름을 통제하는 방식이다.

본 작업은 시험용 MVP가 아니다. 실제 업무에 투입할 수 있는 1차 정식 운영 버전을 완성한다.

## 2. 기존 개발물 처리 원칙

- 현재 저장소와 이미 구현된 업무 규칙, DB, 상태 머신, AI 어댑터, 로컬 게이트웨이를 먼저 조사한다.
- 작동 중인 백엔드 기능은 폐기하거나 처음부터 다시 만들지 않고 재사용한다.
- 별도 웹/PWA 사용자 화면의 신규 개발과 고도화는 중단한다.
- 기존 웹 코드가 있더라도 당장 대규모 삭제하지 않는다.
- 웹/PWA는 운영 진입점과 인수 범위에서 제외하고, Telegram 전환 완료 뒤 정리한다.
- 변경 전 현재 테스트를 실행하고 기준 결과를 기록한다.
- 변경은 작은 단위로 진행하며 기존 기능 회귀를 막는다.

현재 작업 폴더 기준 조사 결과, 아직 실행 가능한 코드 저장소는 없고 문서 산출물만 존재한다. 따라서 기존 코드 재사용/분리 대상은 다음 구현 착수 시 다시 조사한다.

## 3. 확정 사용자 인터페이스

| 항목 | 결정 |
|---|---|
| 프로젝트 UI | 프로젝트 하나당 비공개 Telegram 그룹 하나 |
| 사람 참여자 | 실제 Telegram 계정으로 초대 |
| AI 참여자 | 역할별로 서로 다른 Telegram 봇 계정 사용 |
| 1차 필수 봇 | AI 소대장 봇, Claude Code 분대장 봇, Codex 분대장 봇, 독립 검증자 봇 |
| 봇 정체성 | 고유 이름, username, 프로필 사진 사용 |
| 금지 구조 | 통합 봇 하나가 여러 역할을 연기하는 구조 |
| 제외 범위 | 별도 모바일 앱, 독립 PWA, Telegram Mini App |

## 4. 중앙 오케스트레이터 원칙

Telegram은 대화와 표시 화면이다. 공식 작업 상태의 단일 사실 원천은 중앙 DB다.

각 봇이 그룹 메시지를 보고 제멋대로 자율 반응하지 않는다. 중앙 오케스트레이터가 다음을 결정한다.

- 어느 봇이 발언할지
- 어떤 작업을 어느 AI 실행 어댑터에 배정할지
- 병렬·순차 실행 여부
- 승인 대기 여부
- 검증자 호출 시점
- 수정·재검증 범위
- 완료 보고와 최종 승인 요청

## 5. Bot-to-Bot 통신 원칙

Telegram Bot API 10.x 계열의 bot-to-bot 기능은 기능 플래그로만 사용한다.

기본 경로는 다음이다.

```text
중앙 오케스트레이터 -> 지정된 역할 봇 계정으로 메시지 발신
```

금지한다.

- 봇 메시지를 받은 다른 봇이 자동 반응하며 연쇄 실행
- 봇 간 무한 대화
- 중복 응답
- 순서 역전

필수 안전장치:

- update/message 전역 멱등 처리
- chat/bot별 rate limit
- interaction depth 제한
- 중앙 라우터 기반 권한 및 작업 상태 확인

## 6. 입력 봇과 발언 봇 분리

| 봇 | 기본 역할 |
|---|---|
| AI 소대장 봇 | 기본 명령·대화 입력 창구, 작업 제안 게시 |
| Claude Code 분대장 봇 | 중앙 오케스트레이터 지시 시 Claude Code 작업 관련 발언 |
| Codex 분대장 봇 | 중앙 오케스트레이터 지시 시 Codex 작업 관련 발언 |
| 독립 검증자 봇 | 중앙 오케스트레이터 지시 시 검증 판정과 수정 요구 발언 |

다른 역할 봇이 명령이나 멘션을 직접 받더라도 동일 중앙 라우터로 보내고, 권한·작업 상태 확인 후 처리한다.

## 8. 저장소 책임 배치

기존 모노레포 구조가 있으면 기존 규칙에 맞춰 조정하되, 책임은 유지한다.

| 경로 | 책임 |
|---|---|
| apps/bot-service | 역할별 webhook, 명령, 버튼, 파일 수신, 역할별 메시지 발신 |
| apps/local-gateway | 로컬 PC의 CLI·파일·Git 실행 |
| packages/contracts | Telegram update, 작업, 이벤트, 승인, 검증 공통 스키마 |
| packages/workflow | 상태 머신, DAG, 승인·검증·완료 전이 |
| packages/ai-adapters | Claude Code, Codex 실행 어댑터 |
| packages/telegram-ui | 메시지 템플릿, 인라인 키보드, 상태 표시 |
| supabase | 스키마, 마이그레이션, 권한, 테스트 |

웹/PWA 전용 패키지는 신규 기능 개발 대상에서 제외한다.

## 9. Telegram 연동 요구사항

### 9.1 Webhook

- 역할별 봇마다 HTTPS webhook을 설정한다.
- URL 경로에는 실제 bot token을 넣지 않는다.
- `X-Telegram-Bot-Api-Secret-Token`을 봇별로 검증한다.
- 허용된 `telegram_chat_id`만 처리한다.
- webhook은 빠르게 2xx로 응답하고 장시간 AI 작업은 큐/아웃박스로 넘긴다.
- Telegram 재전송을 전제로 멱등 처리한다.

### 9.2 식별·권한

- 사용자 권한은 `telegram_user_id`로 판정한다.
- 프로젝트방은 `telegram_chat_id`로 판정한다.
- username, 표시명, 프로필 문구를 권한 근거로 사용하지 않는다.
- 방장만 작업 승인·반려·최종 승인·AI 봇 편성 변경을 할 수 있다.
- 봇 관리자 권한은 필요한 항목만 최소로 부여한다.

### 9.3 비밀정보

- 역할별 bot token은 환경 비밀 또는 비밀관리 서비스에 보관한다.
- bot token 원문을 DB, 로그, Telegram 메시지, AI 프롬프트에 넣지 않는다.
- 중앙 DB에는 `token_secret_ref`만 저장한다.
- Claude Code·Codex 로그인 정보와 API 키는 로컬 PC의 공식 인증 저장소에 유지한다.

## 10. 최소 데이터 모델 변경

기존 테이블과 중복되면 새로 만들지 말고 필드를 확장한다.

| 객체 | 필드/규칙 |
|---|---|
| rooms | room_id, telegram_chat_id, owner_telegram_user_id, status |
| room_members | room_id, telegram_user_id, role, permissions, status |
| ai_actors | actor_id, role, adapter_type, status |
| telegram_bots | telegram_bot_id, bot_username, actor_id, token_secret_ref, status |
| telegram_updates | telegram_bot_id, update_id, telegram_chat_id, telegram_message_id, received_at, processed_at, status |
| message_bindings | 내부 event_id/task_id/report_id와 Telegram chat_id/message_id의 연결 |
| 기존 유지·확장 | tasks, approvals, verifications, artifacts, events, outbox |

필수 고유 제약:

- `(telegram_bot_id, update_id)` unique
- `(telegram_chat_id, telegram_message_id)` unique where applicable
- `telegram_chat_id`와 `telegram_user_id`는 64비트 정수로 안전하게 저장

## 11. Telegram 명령과 기본 UX

초기 버전은 Telegram 기본 기능만 사용한다.

| 명령/버튼 | 기능 |
|---|---|
| /newtask | 작업 제안 생성 |
| /tasks | 전체 작업 요약 |
| /task `<id>` | 작업 상세 |
| /search `<단어>` | 작업 검색 |
| /trace `<task_id>` | 이벤트·산출물 URI·검증 이력 조회 |
| /approve `<id>` 또는 [승인] | 작업 승인 |
| /reject `<id>` 또는 [반려] | 작업 반려 |
| /verify `<id>` | 검증 요청 |
| /done `<id>` | 최종 승인 요청/처리 |
| /cancel `<id>` | 취소 요청 |
| /help | 사용법 |

작업 제안 메시지 버튼:

- [승인]
- [수정 요청]
- [반려]

검증·완료 메시지 버튼:

- [재검증]
- [보완 요청]
- [최종 승인]

`/tasks` 결과와 고정된 프로젝트 현황 메시지로 별도 대시보드를 대체한다. 가능한 경우 새 메시지를 계속 쌓지 않고 편집 갱신한다.

## 12. 핵심 처리 흐름

1. 사람이 Telegram 프로젝트방에서 요청한다.
2. AI 소대장 봇이 작업 제안을 구조화해 게시한다.
3. 방장이 인라인 버튼으로 승인한다.
4. 중앙 서버가 callback 발신자의 user_id와 room 권한을 검증한다.
5. 중앙 DB에 작업 카드·의존관계·실행 요청을 한 트랜잭션으로 기록한다.
6. 아웃박스가 로컬 게이트웨이에 작업을 전달한다.
7. Claude Code 또는 Codex가 실제 작업 폴더에서 실행한다.
8. 중앙 오케스트레이터가 지정된 역할 봇 계정으로 의미 있는 진행 상황만 게시한다.
9. 독립 검증자 봇이 판정과 수정 요구를 게시한다.
10. 원 작업팀이 수정하고 검증자 봇이 재검증한다.
11. 소대장 봇이 완료를 결정하고 방장에게 최종 승인을 요청한다.
12. 방장 최종 승인 후에만 작업 상태를 완료로 변경한다.

## 13. 오류·중복·재시도 기준

- webhook update는 at-least-once 전달로 보고 멱등 처리한다.
- 승인 버튼을 여러 번 눌러도 작업 카드와 상태 전이는 한 번만 발생해야 한다.
- Telegram 메시지 전송 실패는 지수 백오프와 rate-limit 응답의 재시도 시간에 따라 재시도한다.
- 메시지 전송 성공 전에 업무 트랜잭션을 되돌리지 않는다.
- DB 이벤트와 발송은 아웃박스로 분리한다.
- 로컬 게이트웨이가 오프라인이어도 작업 요청을 잃지 않는다.
- 프로세스 재시작 후에도 미처리 update/outbox/작업 attempt를 복구한다.

## 14. 완료 조건

아래를 모두 통과해야 개발 완료다.

- 하나의 비공개 Telegram 그룹에 사람 여러 명과 역할별 AI 봇 네 개를 초대할 수 있다.
- 네 AI 봇이 서로 다른 이름·프로필·계정으로 표시된다.
- 중앙 오케스트레이터가 지정한 봇만 발언하며 중복 응답과 봇 간 무한 대화가 없다.
- Telegram 요청 -> 작업 제안 -> 승인 -> 로컬 Claude Code/Codex 실행 -> 중간보고 -> 독립 검증 -> 수정·재검증 -> 소대장 완료 결정 -> 방장 최종 승인이 종단 작동한다.
- Claude Code와 Codex 모두 실제 작업 폴더에서 실행되고 진행·취소·오류·재시도·결과가 해당 작업에 연결된다.
- 허용되지 않은 사용자·그룹·위조 webhook·중복 update가 실행이나 상태 변경을 일으키지 않는다.
- 봇 토큰, 서버 비밀키, 로컬 CLI 자격증명이 채팅·DB 원문·로그에 노출되지 않는다.
- Telegram 모바일·데스크톱·웹에서 명령·버튼·파일·알림 흐름이 모두 작동한다.
- 설치, 봇 생성·초대, webhook 설정, 운영, 백업, 복구, 업데이트, 장애 대응 문서가 제공된다.
- 실제 프로젝트로 운영 검증을 통과하고 방장이 최종 인수 승인한다.

## 15. 구현 순서

1. 현 저장소·테스트·DB·실행 흐름 조사 및 영향도 보고
2. Telegram 식별자·봇·update·message binding 데이터 모델 추가
3. 역할별 bot token/actor 매핑과 webhook 수신기 구현
4. 권한 검사와 update 멱등 처리 구현
5. 작업 제안·승인·반려·조회 명령과 인라인 버튼 구현
6. 기존 상태 머신·아웃박스·로컬 게이트웨이 연결
7. 역할별 봇 발신 라우터 구현
8. Claude Code·Codex 종단 실행 연결
9. 검증·재검증·최종 승인 흐름 연결
10. 보안·중복·재시도·오프라인 복구·rate limit 테스트
11. 실제 Telegram 그룹에서 종단 운영 검증
12. 기존 웹/PWA 진입점의 운영 제외와 문서 정리

## 16. 금지사항

- Telegram으로 충분한 기능을 별도 웹/PWA로 다시 만들지 않는다.
- 역할별 AI를 통합 봇 하나로 축소하지 않는다.
- 각 봇이 그룹 대화를 보고 독립적으로 자동 반응하게 하지 않는다.
- Telegram 메시지를 공식 작업 상태의 유일한 저장소로 사용하지 않는다.
- 사용자 권한을 username이나 표시명으로 판단하지 않는다.
- bot token을 소스 코드·DB 원문·로그에 저장하지 않는다.
- 기존에 작동하는 백엔드·AI 어댑터·로컬 게이트웨이를 이유 없이 재작성하지 않는다.
