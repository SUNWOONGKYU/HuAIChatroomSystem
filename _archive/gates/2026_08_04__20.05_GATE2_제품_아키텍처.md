# Gate 2 제품 아키텍처 — Telegram 다중 AI 봇 운영 구조

## 1. 목표

Telegram 프로젝트방을 사용자 운영 진입점으로 확정하고, 중앙 오케스트레이터·Supabase·로컬 게이트웨이·AI 어댑터가 실제 업무 흐름을 끝까지 처리하는 구조를 확정한다.

이 문서는 구현 기준이다. 별도 웹/PWA 신규 개발 기준이 아니며, MVP나 프로토타입 범위로 축소하지 않는다.

## 2. 확정 구조

```text
Telegram private group
  ├─ human owner / members
  ├─ AI 소대장 봇
  ├─ Claude Code 분대장 봇
  ├─ Codex 분대장 봇
  └─ 독립 검증자 봇
          │
          ▼
apps/bot-service
  ├─ role webhook adapters
  ├─ command/callback router
  ├─ outbound role bot router
  └─ fast 2xx + outbox enqueue
          │
          ▼
Central orchestrator
  ├─ authorization by telegram_user_id / telegram_chat_id
  ├─ workflow state machine + DAG
  ├─ approval / verification / completion rules
  ├─ event outbox + idempotency
  └─ Supabase Postgres / Storage
          │
          ▼
apps/local-gateway
  ├─ outbound central connection
  ├─ allowed path / adapter / timeout policy
  ├─ Claude Code adapter
  ├─ Codex adapter
  └─ files / Git / watcher / execution events
```

## 3. 운영 원칙

| 원칙 | 확정 |
|---|---|
| 단일 사실 원천 | Telegram 메시지가 아니라 중앙 DB |
| 발언 통제 | 중앙 오케스트레이터가 지정한 역할 봇만 발언 |
| 입력 창구 | AI 소대장 봇이 기본 명령·대화 입력 창구 |
| 역할 봇 | Claude/Codex/검증자 봇은 지시받을 때만 발언 |
| 봇 간 통신 | Bot API 10.x 기능은 보조 플래그, 공식 흐름은 비의존 |
| 중복 방지 | `(telegram_bot_id, update_id)`와 idempotency key 기준 |
| 비밀정보 | bot token 원문, service key, CLI 자격증명은 DB/로그/프롬프트 금지 |

## 4. 패키지 책임

| 패키지 | 책임 |
|---|---|
| apps/bot-service | Telegram webhook 수신, secret 검증, 명령/버튼 파싱, 빠른 ack, outbox enqueue, 역할별 메시지 발신 |
| apps/local-gateway | 중앙 작업 수신, 허용 경로/어댑터/시간 검증, Claude Code/Codex 실행 계획, 실행 이벤트 회수 |
| packages/contracts | Telegram update, callback, actor, task, event, execution 공통 타입 |
| packages/workflow | 작업 상태 머신, 이벤트 전이, 승인·검증·완료 게이트 |
| packages/ai-adapters | Claude Code/Codex 명령 배열 생성 및 어댑터 정책 |
| packages/telegram-ui | 메시지 템플릿, 인라인 키보드, callback data 생성 |
| supabase | Telegram 식별자, 업무 테이블, outbox, message binding, RLS/감사/복구 기준 |

## 5. Telegram 처리 흐름

1. Telegram이 역할별 webhook으로 update를 보낸다.
2. bot-service가 `X-Telegram-Bot-Api-Secret-Token`을 검증한다.
3. 허용된 `telegram_chat_id`인지 확인한다.
4. `(telegram_bot_id, update_id)`로 중복 update를 차단한다.
5. 명령 또는 callback을 중앙 라우터 입력으로 정규화한다.
6. webhook은 장시간 작업을 기다리지 않고 빠르게 2xx를 반환한다.
7. 중앙 오케스트레이터가 DB 트랜잭션으로 작업/승인/이벤트/outbox를 기록한다.
8. outbox consumer가 지정된 역할 봇으로 메시지를 발신하거나 로컬 게이트웨이에 작업을 전달한다.

## 6. 주요 상태 흐름

```text
proposal_pending
  -> scheduled
  -> in_progress
  -> mid_approval_pending
  -> in_progress
  -> verification_pending
  -> revision_in_progress
  -> verification_pending
  -> commander_completion_pending
  -> completion_approval_pending
  -> completed
```

금지 전이:

- 방장 승인 전 `scheduled` 또는 `in_progress` 진입 금지
- 검증자 합격만으로 `completed` 전이 금지
- 검증자가 산출물을 직접 수정하는 전이 금지
- 방장 최종 승인 전 `completed` 전이 금지
- 승인/버튼/update 중복으로 동일 전이 반복 금지

## 7. 데이터 확정

기존 테이블이 있으면 확장하고, 없으면 `supabase/schema.sql` 기준으로 만든다.

필수 Telegram 테이블:

- `rooms`
- `room_members`
- `ai_actors`
- `telegram_bots`
- `telegram_updates`
- `message_bindings`

필수 업무 테이블:

- `tasks`
- `approvals`
- `verifications`
- `artifacts`
- `events`
- `outbox`

필수 실행 테이블:

- `gateway_instances`
- `execution_attempts`

## 8. 보안 경계

- 권한 판단은 `telegram_user_id`와 DB membership으로 한다.
- 프로젝트 판단은 `telegram_chat_id`로 한다.
- username, 표시명, 프로필 사진은 권한 근거로 쓰지 않는다.
- bot token은 `token_secret_ref`만 DB에 저장한다.
- 로컬 게이트웨이는 중앙으로 outbound 연결만 만든다.
- 로컬 실행은 실행 파일과 인수 배열로만 계획한다.
- 허용 경로, 어댑터, timeout, 비용/네트워크 정책을 작업별로 검사한다.

## 9. Gate 2 완료 기준

- Telegram 중심 아키텍처가 문서와 코드 골격에 반영된다.
- PWA 신규 개발 경로가 운영 진입점에서 제외된다.
- 역할별 봇 4개와 중앙 오케스트레이터 발언 통제 구조가 계약에 반영된다.
- Telegram update/callback/message binding/idempotency가 계약과 DB에 반영된다.
- 로컬 게이트웨이와 Claude Code/Codex 어댑터 실행 계획이 분리된다.
- 상태 머신이 3단계 완료 승인과 검증자 수정 금지를 표현한다.
- 구조 검증이 통과한다.
